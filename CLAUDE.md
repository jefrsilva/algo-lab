# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

"Visualizador de Estruturas de Dados & Algoritmos" — a browser-based, vanilla-JS (no framework) tool for visualizing pointer/memory-model programs written in a small Python-like DSL. No backend; everything runs client-side. Code comments and UI strings are in Portuguese (pt-BR); match that when editing existing files.

## Commands

```bash
npm run dev       # Vite dev server, http://localhost:5173
npm run build     # production build to dist/
npm run preview   # preview a production build
```

There is no test suite, no linter, and no type checker configured in this repo (`package.json` only has the three Vite scripts). Verify changes by running the app in a browser and exercising the feature manually (the `.claude/launch.json` dev-server config is named `algo-visualizer`, port 5173).

## Big-picture architecture

`src/main.js` does one thing: `new App(root)` from [src/app/App.js](src/app/App.js). Everything else hangs off that one class, which builds the entire DOM UI by hand (`document.createElement`, no JSX/templates) and owns all top-level state.

### Two view modes sharing one codebase — only one is reachable

The app has two parallel "modes" that both existed as full features, but **only micro mode is currently wired into the UI**:

- **Macro mode** (legacy): classic data-structure visualization — build a list/stack/queue/tree/graph on a canvas, then watch BFS/DFS animate over it step-by-step. Its model classes ([src/core/structures/](src/core/structures/): `LinkedList`, `Stack`, `Queue`, `BinaryTree`, `Graph`), renderer ([src/render/CanvasView.js](src/render/CanvasView.js), [src/render/layouts.js](src/render/layouts.js)), and UI ([src/ui/Sidebar.js](src/ui/Sidebar.js), [src/ui/PlaybackControls.js](src/ui/PlaybackControls.js)) are all still fully implemented and wired together inside `App.js`, but per comments in `App.js` (`_buildLayout`) the containers holding this mode are **never appended to the visible DOM** — there is no button that reaches it anymore. It's kept intact (not deleted) because other methods in `App.js` assume these objects exist. Don't be surprised to find dead-but-functional code paths here; when adding features, assume you're extending **micro mode** unless told otherwise.
- **Micro mode** (active): what the app actually opens into. Visualizes a lower-level "memory model" — structs (nodes with data/next/prev), pointers, arrays, dicts, and scalar variables, laid out and connected by hand on an SVG canvas, and/or driven by writing DSL code against that model with recursion shown as a call-tree of frames.

Both modes share the same underlying DSL/interpreter — macro mode's "Run" feature (BFS/DFS as code, not a hand-coded animation) reuses the exact same lexer/parser/interpreter as micro mode, just against a different `Environment` implementation (see below). If you need to touch the interpreter, changes affect both modes.

### The DSL and its interpreter (`src/interpreter/`)

A small Python-flavored language (assignment incl. `+=`/`-=`/etc., `if/elif/else`, `while`, chained comparisons (`0 <= i < n` — a `Compare` AST node, each operand evaluated once), negative indices on lists/matrices (normalized in the adapters, so read cursors like `nums[-1]` work), `for x in <array|range(...)|enumerate(...)>`, `def f(a, b=default): ... return`, `break/continue`, list/dict/set literals (a set is stored in `MicroModel` as an array flagged `isSet` — drawn without indices, `add`/`remove`/`discard` instead of positional ops; element order replicates CPython 3.11's hash table exactly via [pyset.js](src/interpreter/pyset.js), whose serialized table lives on the array as `hashTable` — always replace it, never mutate, since playback snapshots share it), `deque` (`deque()`/`deque(iterável, maxlen=n)`/`collections.deque(...)`, with `from collections import deque`/`import collections` accepted as no-op `Import` statements — any other import is a parse error; stored in `MicroModel` as an array flagged `isDeque` + `maxlen`, drawn like a list with a "⇄ deque" caption; `append`/`appendleft`/`pop`/`popleft`/`extend`/`extendleft`/`rotate`/`reverse`/`clear`/`count`/`index` live in `evaluator.js#callDequeMethod`, built on the adapters' list primitives plus `isDeque`/`dequeMaxlen`/`dequeSetItems`; holds values OR nodes, like any list — see `MicroRuntimeAdapter#_fitArrayKind`: an EMPTY list/deque takes the kind of the first item appended/inserted (so `fila = []` + `fila.append(raiz)` works for BFS; a graph node's `neighbors` list stays node-only), and mixing nodes and values warns), lists of nodes as values (`[raiz]`, `[None] * n`, `[a] + filhos`, node list comprehensions, `list(...)`/slices of a node list — a `{kind:'nodelist', items}` value in `evaluator.js#listValueFrom`, turned into a `kind:'ref'` array by the adapters; `==`/`+`/`*` with a live list compare/combine by content via `materializeList`), keyword arguments (`nome=valor` — only `deque(..., maxlen=n)` and user `def` functions accept them, see `interpreter.js#tryUserCall`; any other builtin warns), tuples (`(a, b)`, `d[i, j]`, `t = a, b`, `i, j = t` — immutable; with only number/text/bool/None/tuple items they can be dict keys, set elements and be stored in variables/dict cells/list cells as an interned `PyTuple` from [pytuple.js](src/interpreter/pytuple.js), so equal tuples are the same JS object and work as `Map` keys and with `===`; `pyset.js` hashes them with CPython's exact `tuplehash`; tuples containing nodes can't be stored yet), f-strings with `!r`/`:spec`/`{x=}` — lexed in `lexer.js#readFStringParts`, formatted by [format.js](src/interpreter/format.js) —, `Node(v)` to allocate a struct), one statement per line, no classes, no nested `def`.

Pipeline: **[lexer.js](src/interpreter/lexer.js)** (tokenizes one line) → **[parser.js](src/interpreter/parser.js)** (`parseStatement`, recursive-descent, one line → one AST node, per `ast.js` shapes) → **[blockParser.js](src/interpreter/blockParser.js)** (`parseProgram`, groups lines into a full program via Python-style indentation, extracts top-level `def`s into a `functions` map) → **[interpreter.js](src/interpreter/interpreter.js)** (`runProgram`, a **generator** that executes the whole program and `yield`s one "step" per meaningful action — this is what powers step-by-step playback) → **[evaluator.js](src/interpreter/evaluator.js)** (`evaluate`/`assign`, the actual expression/assignment semantics, walking AST nodes into typed values like `{kind:'struct'|'array'|'dict'|...}`).

Crucially, `evaluator.js` and `interpreter.js` are **model-agnostic**: they operate through a duck-typed `Environment` interface (`resolveName`, `assignName`, `getAttr`, `setAttr`, etc.), never touching `MicroModel` or the legacy structures directly. The two concrete environments are:

- [src/app/MicroRuntimeAdapter.js](src/app/MicroRuntimeAdapter.js) — read/write `Environment` over `MicroModel`. Owns `frameStack` for recursion (each call gets its own pointer/variable scope; structs/arrays/dicts are the shared "heap" visible from any frame) and tracks `touched` cells for highlighting.
- [src/app/MacroRuntimeAdapter.js](src/app/MacroRuntimeAdapter.js) — read-mostly `Environment` over a legacy structure (`Graph`, etc.); the DSL program is an *algorithm running over* an already-built structure, not something that builds the structure itself. Tracks `nodeStates` (current/visited) and an `output` print buffer.

If you add a new builtin, operator, or statement type to the DSL, it likely needs support in `evaluator.js`/`interpreter.js` plus both adapters (since both must remain able to run the same programs).

### Running a program end to end

- **Micro**: `CodeEditor` source → `blockParser.parseProgram` → `interpreter.runProgram` against `MicroRuntimeAdapter` → mutates `MicroModel` → [src/app/MicroProgramRunner.js](src/app/MicroProgramRunner.js) captures a full model **snapshot after every step** (stepping back restores a snapshot, since each line actually mutates shared state — this is why micro-mode playback differs from macro's) → [src/render/MicroCanvasView.js](src/render/MicroCanvasView.js) renders.
- **Macro "Run"**: source (see [src/app/macroExamplePrograms.js](src/app/macroExamplePrograms.js) for the BFS/DFS examples, using `inicio`/`atual.vizinhos` conventions) → `blockParser` → `interpreter.runProgram` against `MacroRuntimeAdapter` → [src/algorithms/runMacroProgram.js](src/algorithms/runMacroProgram.js) repackages each interpreter tick into a step object (`{seq, pseudoLine, description, auxIds, visited, currentId, edge, output}`) → `CanvasView` renders. `pseudoLine` points at the real source line so the code editor highlights the executing line directly (no separate canned pseudocode). `currentId`/`visited` come from explicit `marcar_atual`/`marcar_visitado` calls in the DSL program (evaluator builtins), not name-based inference.

### Rendering layer (`src/render/`)

Both canvases are hand-rolled SVG, pure/dumb renderers driven by already-positioned world-coordinate state (no interaction logic — that lives in `App.js`):

- [CanvasView.js](src/render/CanvasView.js) — macro-mode renderer (frames/nodes/edges, pan/zoom).
- [MicroCanvasView.js](src/render/MicroCanvasView.js) (largest render file) — micro-mode renderer, plus the geometry/layout constants and port functions (`structPrevPort`/`structNextPort`, `pointerPort`, `arrayLayout`, `dictLayout`, `arrayHandleRect`/`dictHandleRect`/`matrixHandleRect` — the tab left of a horizontal array/dict / above a vertical one / left of a matrix, outside the `*Layout` boxes, that is the drop target for linking a pointer to the whole collection and a drag handle; `boxWithHandle` gives box+tab bounds for the selection halo, whole-collection arrows and App bounds, etc.) that define visual layout and the "connector pin" hit-targets used for drag-to-link gestures.
- [layouts.js](src/render/layouts.js) — pure layout algorithms for macro structures (list/queue/stack/tree/force-directed graph layout) that turn a structure's generic `toGraph()` output into positions.
- [svgUtils.js](src/render/svgUtils.js) — tiny `svgEl(tag, attrs)` helper for namespaced SVG element creation.

### UI widgets (`src/ui/`)

Small, single-purpose classes instantiated and wired together by `App.js` (no shared base class/framework): `CodeEditor` (own syntax highlighting + live per-line validation via `parser.js`, used by both macro and micro run modes), `CallTree` (renders `interpreter.js`'s call tree for recursion; only grows during playback), `PlaybackControls` (step/play/speed bar, shared by both modes), `NodePopup`/`ArraySettingsPopup`/`LabelSettingsPopup`/`ChartSettingsPopup` (floating settings popups — the last one is the right-click menu of a Big-O complexity chart: which of O(1)/O(log n)/O(n)/O(n log n)/O(n²) to draw, the scale (`nMax`, and `yMode` manual `yMax` or auto = fits the largest checked function at nMax, see `chartYMax`) and the two axis titles; charts live in `App#microCharts` like areas — canvas-only, outside `MicroModel`, movable, resizable with the area handles, created by the "Gráfico" toolbar mode (4/B) or `new chart`; geometry in `MicroCanvasView.js#chartLayout`), `InlineValueEditor` (in-place value editing overlay — on the micro canvas a single click only selects; every in-place edit (node data, array/dict/matrix cell, variable value/name, pointer/collection name, label text) is opened by double-click, see `App#_onMicroDblClick`; removing is Delete/Backspace), `ModeToolbar` (interaction-mode switcher), `DragHintLabel` (cursor-following hint during drag), `CanvasTitle` (editable canvas title overlay), `ConsoleWindow` (micro-mode `print` console, docked under the canvas or as a movable/resizable translucent window over it; mode + geometry persisted via `settings.js`), `AppMenu` (hamburger dropdown: project actions, quick actions, "Configurações…"), `SettingsDialog` (modal settings window — theme, code font size, simplified nodes, full names, area grid snap, code panel, console visibility (C) and position (Alt+C), call-tree mode, playback speed; changes apply live through `App#_applySetting`, the same path the keyboard shortcuts G/N/C/Alt+C/Ctrl+A/Ctrl+H use; all user-preference state lives in one localStorage object in [src/app/settings.js](src/app/settings.js) — add new preferences there, not as new menu toggles or ad-hoc localStorage keys), `QuickActionPalette` (Ctrl+Space command box — abbreviated matching like `n p` → `new pointer`, gray ghost of the command Enter would run; shows at most 3 runnable matches once something is typed, the full list only when opened from the ☰ menu (`showAll`); the commands themselves live in `App#_openQuickActions`, each `new <element>` creating the element at the viewport center and opening in-place editing of its name/data, Esc undoing the creation; typing `nums[i]`/`m[i][j]` as a new pointer's name turns it into a real read cursor via `MicroRuntimeAdapter#adoptReadCursor` (dragging out of an array's index strip, or Shift+drag/Shift+click on an array or matrix cell, creates that same read cursor, `nums[2]`/`m[1][0]`, directly — no name editing, see `App#_findMicroCursorCellAt`/`_startMicroIndexCursorDrag`); also `new sliding window`/`remove sliding window`, which group 2 Ctrl+click-selected cursors on the same array — stored in `App#microWindows` by stable cursor key (`nums[l]`), not by id, so a window survives playback steps, re-runs and save/load; selecting one cursor selects both and lights every cell between them; an always-visible bracket under those cells is drawn by `MicroCanvasView#_renderWindowBrackets`), `Sidebar` (legacy macro-mode structure picker — currently unreachable, see above).

### Core models (`src/core/`)

- [micro/MicroModel.js](src/core/micro/MicroModel.js) — the micro mode's data model: five `Map`s (`structs`, `pointers`, `arrays`, `dicts`, `variables`), no rendering knowledge, just CRUD that keeps references consistent on deletion (nulls out dangling pointers/cells). Pointers/variables carry a `frameId` (`'global'` or a call-frame id) for recursion display; structs/arrays/dicts have none — they're the shared heap.
- [structures/](src/core/structures/) — legacy macro data structures (`LinkedList`, `Stack`, `Queue`, `BinaryTree`, `Graph`), each exposing a generic `toGraph()` for the macro layout functions.
- [id.js](src/core/id.js) — `nextId(prefix)`, the single id-generation utility used everywhere.

## Things worth knowing before making changes

- `App.js` is intentionally monolithic and large; read the specific method/section you need (grep for it) rather than the whole file — many sections have explanatory Portuguese comments describing *why*, not just what.
- When you see macro-mode code that looks unreachable or oddly disconnected from any visible UI, that's expected (see "only micro mode is reachable" above) — don't assume it's dead code to delete without checking `App.js` comments first.
- The DSL's `interpreter.js`/`evaluator.js` are shared between both modes via the `Environment` interface — changes there ripple to both `MicroRuntimeAdapter` and `MacroRuntimeAdapter`.
- There's no automated test suite; changes must be verified by running `npm run dev` and exercising the UI directly.
