# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

"Visualizador de Estruturas de Dados & Algoritmos" — a browser-based, vanilla-JS (no framework) tool for visualizing pointer/memory-model programs written in a small Python-like DSL. No backend; everything runs client-side. Code comments and UI strings are in Portuguese (pt-BR); match that when editing existing files.

## Language of commits, PRs and comments (always pt-BR)

Everything written for this repository is in **Brazilian Portuguese (pt-BR)**, always — even when the request or the surrounding conversation is in English:

- **commit messages** (title and body; e.g. `Corrige cor do colchete da sliding window`), merge-commit messages and branch descriptions;

## Commands

```bash
npm run dev       # Vite dev server, http://localhost:5173
npm run build     # production build to dist/
npm run preview   # preview a production build
npm test          # Vitest suite in tests/ (run once)
npm run test:watch
```

Automated tests live in `tests/` (Vitest; see [tests/README.md](tests/README.md)): DSL programs whose output must match real Python (`tests/dsl/casos.js`, and `python.test.js` checks that answer key against `python3` when available), interpreter units (lexer/parser/blockParser/format/pyset/pytuple), `MicroModel`, `MicroProgramRunner`/`MicroRuntimeAdapter`/settings, the Big-O chart readout geometry and the labels' markdown parser/layout (`tests/render/`), and a jsdom integration test that mounts the whole `App` (Simulação, playback, Sandbox Ctrl+Enter, shortcuts, quick actions, save/load). Known DSL-vs-Python gaps are pinned in `tests/dsl/bugs-conhecidos.test.js` with `test.fails` — fixing one makes its test fail, so flip it to `test`. CI (`.github/workflows/testes.yml`) runs `npm test` + `npm run build` on pushes to `main` and on PRs. Add a test with every change; there is still no linter or type checker. jsdom does no layout, so drawing/geometry still needs a browser check (the `.claude/launch.json` dev-server config is named `algo-visualizer`, port 5173).

`node scripts/run-dsl.mjs <arquivo.py|->` runs a DSL program headlessly in Node through the same path as Simulação (`--steps` lists the steps, `--model` dumps the final `MicroModel`) — the fastest way to check interpreter changes.

## Big-picture architecture

A detailed onboarding reference (pt-BR) — per-file responsibilities, end-to-end flows and step-by-step recipes for common tasks (new DSL builtin, new visual element, new toolbar tool, new setting…) — lives in [docs/ARQUITETURA.md](docs/ARQUITETURA.md). Keep it in sync when changing architecture.

`src/main.js` does one thing: `new App(root)` from [src/app/App.js](src/app/App.js). Everything else hangs off that one class, which builds the entire DOM UI by hand (`document.createElement`, no JSX/templates) and owns all top-level state.

### Micro mode (the only mode)

The app visualizes a lower-level "memory model" — structs (nodes with data/next/prev), pointers, arrays, dicts, and scalar variables, laid out and connected by hand on an SVG canvas, and/or driven by writing DSL code against that model with recursion shown as a call-tree of frames. (An older "macro" mode — prebuilt list/stack/queue/tree/graph frames with BFS/DFS animations — was removed; everything it did is doable in micro mode. Many identifiers keep the `micro` prefix from that era.)

### The DSL and its interpreter (`src/interpreter/`)

A small Python-flavored language (assignment incl. `+=`/`-=`/etc. — `lista += ...` extends the same list in place (`BinOp.inplace`), like Python; any name can be rebound to any value, like Python (`x = x + [2]`, `res = res + a[i:]`, `d = {}` again, `x = 5` then `x = Node(1)`: a collection is rewritten in place when nothing else references it, else the old one stays, unnamed, for its aliases and the name label moves to the new one; unnamed collections nobody reaches are dropped — see `MicroRuntimeAdapter#assignName`/`_isShared`/`_dropIfOrphan`; `a, b = b, a` goes through `evaluator.js#assignTuple`); assignment inside a function always binds a local name (no `global`), so `raiz = inserir(raiz, v)` with a same-named parameter works, `if/elif/else`, `while`, the conditional expression `a if cond else b` (`IfExp`, lowest precedence; only the chosen branch is evaluated, also for user-function calls in `interpreter.js#resolveUserCalls`), chained comparisons (`0 <= i < n` — a `Compare` AST node, each operand evaluated once), negative indices on lists/matrices (normalized in `MicroRuntimeAdapter`, so read cursors like `nums[-1]` work; a list read through an expression — `res[i][j]`, `d[k][i]` — names its read cursor after the whole expression and re-evaluates it via `readCursorObjectNode`), `for x in <array|range(...)|enumerate(...)>`, `def f(a, b=default): ... return`, `break/continue`, builtins incl. `abs()`, `float(x)` (mainly `float('inf')`/`float('-inf')`, shown as `inf`/`-inf` via `core/numText.js`), `int(x[, base])`, `ord()`/`chr()` (and `print(d.values())` shows `dict_values([...])`, like `dict_keys`/`dict_items` — an optional `label` on the `iter`/`pairs` values), indexing/slicing any list value (`sorted(nums)[::-1]`, `d[k][1:]`), list/dict/set literals (a dict literal can hold lists — `{"a": [1, 2]}` links the cell to an anonymous array, same path as `d[k] = [..]`, `MicroRuntimeAdapter#_writeDictCell` — and `print`/`str`/f-strings expand them; a set is stored in `MicroModel` as an array flagged `isSet` — drawn without indices, `add`/`remove`/`discard` instead of positional ops; element order replicates CPython 3.11's hash table exactly via [pyset.js](src/interpreter/pyset.js), whose serialized table lives on the array as `hashTable` — always replace it, never mutate, since playback snapshots share it), `deque` (`deque()`/`deque(iterável, maxlen=n)`/`collections.deque(...)`, with `from collections import deque`/`import collections` accepted as no-op `Import` statements — any other import is a parse error; stored in `MicroModel` as an array flagged `isDeque` + `maxlen`, drawn like a list with discreet "início"/"fim" captions on its first/last cell (stacked in two lines when one element is both) plus a separate `maxlen=n` one — `MicroCanvasView.js#arrayEndCaptions`, which also gives a list in Pilha orientation its "topo" caption; outside the layout, but `arrayOuterBox`/`App#_microArrayOuterRect` count them when looking for free space, so new elements don't cover them; `append`/`appendleft`/`pop`/`popleft`/`extend`/`extendleft`/`rotate`/`reverse`/`clear`/`count`/`index` live in `evaluator.js#callDequeMethod`, built on `MicroRuntimeAdapter`'s list primitives plus `isDeque`/`dequeMaxlen`/`dequeSetItems`; holds values OR nodes, like any list — see `MicroRuntimeAdapter#_fitArrayKind`: an EMPTY list/deque takes the kind of the first item appended/inserted (so `fila = []` + `fila.append(raiz)` works for BFS; a graph node's `neighbors` list stays node-only), and mixing nodes and values warns), lists of nodes as values (`[raiz]`, `[None] * n`, `[a] + filhos`, node list comprehensions, `list(...)`/slices of a node list — a `{kind:'nodelist', items}` value in `evaluator.js#listValueFrom`, turned into a `kind:'ref'` array by `MicroRuntimeAdapter`; `==`/`+`/`*` with a live list compare/combine by content via `materializeList`), lists of lists (`[[1], [2, 3]]`, `res = []` + `res.append([1, 2])`, `[[] for _ in range(k)]`, `list(d.values())`, `[a, b]` with live lists — a `{kind:'nestedlist', items}` value whose items are live lists (`arrayref`, kept BY REFERENCE, like Python), new lists or None; `MicroRuntimeAdapter#_fillArray`/`_listCellId` turn it into a `kind:'arrayref'` array whose cells hold the ids of anonymous inner arrays (named `res[0]`…, born below the outer one via `createPosition(..., {belowArrayId})`, dropped when nothing reaches them — a list popped out of a cell waits in `pendingOrphans` until `collectOrphans` at the end of the statement, so `x = res.pop()` keeps it; cycles are refused); `==`/`in`/`remove` compare by content at any depth (`evaluator.js#materializeDeep`); code no longer creates matrices: NEW lists of values all of the same length (`[[1, 2], [3, 4]]`, `[[0] * c for _ in range(l)]`) are a `nestedlist` flagged `grid`, born with `orientation: 'grid'` — drawn as a table, see `layoutGrids` below — so rows can be appended, change length, be aliased (`row = m[0]`) and iterated (`for row in m`); the same item repeated (`[[0] * 3] * 3`) becomes ONE list in several cells, like Python), keyword arguments (`nome=valor` — only `deque(..., maxlen=n)` and user `def` functions accept them, see `interpreter.js#tryUserCall`; any other builtin warns), tuples (`(a, b)`, `d[i, j]`, `t = a, b`, `i, j = t` — immutable; with only number/text/bool/None/tuple items they can be dict keys, set elements and be stored in variables/dict cells/list cells as an interned `PyTuple` from [pytuple.js](src/interpreter/pytuple.js), so equal tuples are the same JS object and work as `Map` keys and with `===`; `pyset.js` hashes them with CPython's exact `tuplehash`; tuples containing nodes can't be stored yet), f-strings with `!r`/`:spec`/`{x=}` — lexed in `lexer.js#readFStringParts`, formatted by [format.js](src/interpreter/format.js) —, `Node(v)` to allocate a struct; `ListNode(v)` is a singly linked node — type `'slist'`, only `data`/`next`, drawn as a 2-cell box like GraphNode's, `new list node` quick action, `.prev` ignored — `TreeNode(v)`/`GraphNode(v)` the tree/graph variants), one statement per line — but, like Python, a statement continues on the next lines while a `(`/`[`/`{` is open or the line ends in `\` (`blockParser.js#joinLogicalLine`; it keeps the line where it starts, and `logicalLineAt` lets Sandbox Ctrl+Enter run it whole) —, no classes, no nested `def`.

Pipeline: **[lexer.js](src/interpreter/lexer.js)** (tokenizes one line) → **[parser.js](src/interpreter/parser.js)** (`parseStatement`, recursive-descent, one line → one AST node, per `ast.js` shapes) → **[blockParser.js](src/interpreter/blockParser.js)** (`parseProgram`, groups lines into a full program via Python-style indentation, extracts top-level `def`s into a `functions` map) → **[interpreter.js](src/interpreter/interpreter.js)** (`runProgram`, a **generator** that executes the whole program and `yield`s one "step" per meaningful action — this is what powers step-by-step playback) → **[evaluator.js](src/interpreter/evaluator.js)** (`evaluate`/`assign`, the actual expression/assignment semantics, walking AST nodes into typed values like `{kind:'struct'|'array'|'dict'|...}`).

Crucially, `evaluator.js` and `interpreter.js` are **model-agnostic**: they operate through a duck-typed `Environment` interface (`resolveName`, `assignName`, `getAttr`, `setAttr`, etc.), never touching `MicroModel` directly. The concrete environment is:

- [src/app/MicroRuntimeAdapter.js](src/app/MicroRuntimeAdapter.js) — read/write `Environment` over `MicroModel`. Owns `frameStack` for recursion (each call gets its own name scope — assignment always binds in the current frame, lookup goes current frame then global; structs/arrays/dicts/matrices are the shared "heap" visible from any frame, and collections created in a call disappear when it ends unless still reachable (`releaseDeadArrays`)) and tracks `touched` cells for highlighting.

If you add a new builtin, operator, or statement type to the DSL, it likely needs support in `evaluator.js`/`interpreter.js` plus `MicroRuntimeAdapter`.

### Running a program end to end

`CodeEditor` source → `blockParser.parseProgram` → `interpreter.runProgram` against `MicroRuntimeAdapter` → mutates `MicroModel` → [src/app/MicroProgramRunner.js](src/app/MicroProgramRunner.js) captures a full model **snapshot after every step** (stepping back restores a snapshot, since each line actually mutates shared state) → [src/render/MicroCanvasView.js](src/render/MicroCanvasView.js) renders.

also `new sliding window`/`remove sliding window`, which group 2 Ctrl+click-selected cursors on the same array — stored in `App#microWindows` by stable cursor key (`nums[l]`), not by id, so a window survives playback steps, re-runs and save/load; selecting one cursor selects both and lights every cell between them; the window carries one `color` shared by both cursors and its bracket (picked on creation — a cursor's existing color or an unused palette color —, changed by Alt+1…Alt+0 on either cursor, applied over `microColors` by `App#_microEffectiveColors`, kept by the cursors when the window is removed); an always-visible bracket under those cells (right of them on a vertical array) is drawn by `MicroCanvasView#_renderWindowBrackets` — it flips to the top/left when an arrow of one of the window's own cursors arrives from below/the right and would cross it, see `_windowBracketSide`; other pointers' arrows don't count).

### Core models (`src/core/`)

- [micro/MicroModel.js](src/core/micro/MicroModel.js) — the micro mode's data model: six `Map`s (`structs`, `pointers`, `arrays`, `dicts`, `matrices`, `variables`), no rendering knowledge, just CRUD that keeps references consistent on deletion (nulls out dangling pointers/cells). Pointers/variables carry a `frameId` (`'global'` or a call-frame id) for recursion display; structs/arrays/dicts/matrices are the shared heap (an array's/dict's/matrix's `frameId` only scopes its *name*).
- [id.js](src/core/id.js) — `nextId(prefix)`, the single id-generation utility used everywhere.

### Where new elements' pointers are born

A pointer born together with its element — the name-label pointer of a list/set/deque/dict/matrix (from code or Ctrl+Space `new array`/…) and `p` in `p = Node(1)` — is placed `MICRO_ARROW_GAP` (48) away so its arrow is visible: to the LEFT of collections and GraphNodes, ABOVE (centered) Node/TreeNode (`App#_microPointerSpotNear`). `MicroRuntimeAdapter` only asks for this (`createPosition(..., near)`) when the struct isn't referenced by anything yet (`_structReferenced`), so `q = p` is unaffected. If the spot is taken and the element is also fresh (not at a remembered `microLayout` position — `on*Created(node, {movable})`), element and pointer move together to free space (`_microMoveWithPointer`); a new GraphNode's neighbors array (from code via the adapter's `onStructCreated` hook, pointer or not; Ctrl+Space `new graph node`; or created by the Ligar nós tool on an old node) is placed `MICRO_ARROW_GAP` away by `_microTidyOwned` — to the RIGHT, vertically centered, if free, else BELOW (right-aligned), else to the right with node + list moved together as a block (`_microMoveBlock`; with `movable: false` the node stays and the list searches further right), never on the left where the pointer goes; Shift+click read cursors are also born `MICRO_ARROW_GAP` from their cell; on a re-run a fresh node is placed relative to its remembered global pointer (`_microPlaceUnderPointer`).

## Things worth knowing before making changes

- `App.js` is intentionally monolithic and large; read the specific method/section you need (grep for it) rather than the whole file — many sections have explanatory Portuguese comments describing *why*, not just what.
- The DSL's `interpreter.js`/`evaluator.js` talk to the model only through the `Environment` interface — changes there usually need a matching change in `MicroRuntimeAdapter`.
- Commit messages, PR titles/descriptions and GitHub comments are written in pt-BR (see "Language of commits, PRs and comments" above).
- Run `npm test` before committing and add tests for what you change (where each kind of test goes: [tests/README.md](tests/README.md)). The suite can't see rendering — visual changes still need `npm run dev` (or the Playwright smoke test) and a look at the canvas.
